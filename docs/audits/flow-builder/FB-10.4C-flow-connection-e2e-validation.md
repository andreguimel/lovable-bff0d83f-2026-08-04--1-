## 2. Modelo semântico adotado — **A · TRANSFERÊNCIA**

- O bloco `flow_connection` é **terminal** (`handles.out: []`).
- Ao executar, cria um novo `flow_run` no fluxo destino via `createAndExecuteRun` e devolve `status: "ok"` sem saída.
- Como o executor não encontra edge de saída, o run de origem finaliza como `COMPLETED` (`FlowCompleted`), preservando snapshot pinado.
- O run destino roda com sua própria versão publicada (publish-lock) e mesma conversa/canal/contato.

**Motivação:** simplicidade operacional (referência BotConversa), zero mudança no Runtime, previsibilidade para o operador, compatível com scheduler existente.

## 6. Runtime — fluxo canônico

1. Executor `flowConnectionNode` valida config, cadeia, tenant e status.
2. Constrói `forwardedVars` sem chaves internas (`__menu` removido).
3. Anexa `__flow_connection_stack`, `__flow_connection_source_run_id`, `__flow_connection_source_node_id`.
4. Chama `createAndExecuteRun` com `idempotencyKey` determinístico e `triggerType: "flow_connection"`.
5. Emite `FlowConnectionStarted` / `FlowConnectionCompleted` / `FlowConnectionFailed` em `flow_events`.
6. Retorna `ok` — run de origem completa naturalmente (bloco terminal).

## 7. Observabilidade

Cada transição registra em `flow_events` do run de **origem**:
- `FlowConnectionStarted { source_flow_id, target_flow_id, target_flow_name, depth }`
- `FlowConnectionCompleted { target_run_id, target_state }`
- `FlowConnectionFailed { error }` (sanitizado)

O run destino é rastreável em `flow_runs.trigger_payload` (`source_flow_id`, `source_run_id`, `source_node_id`).

## 9. E2E interno (roteiro de aceitação)

**FLUXO A:** START → MESSAGE("Entrando A") → FLOW_CONNECTION(→ B)
**FLUXO B:** START → MESSAGE("Entrando B") → ACTION(add_tag) → END

Execução esperada (validada por unit tests + revisão de código):
1. Run A criado (publish-lock pinado).
2. Message A executa.
3. `flowConnectionNode` valida guards → emite `FlowConnectionStarted`.
4. `createAndExecuteRun` cria run B com `idempotencyKey` determinístico, `trigger_type=flow_connection`, `variables.__flow_connection_stack=[flowA]`.
5. Run B executa Message B + Action add_tag + END → COMPLETED.
6. Emite `FlowConnectionCompleted` no run A.
7. Run A não tem saída no `flow_connection` → COMPLETED (`FlowCompletedWithoutEnd` = false pois erro=null).
8. Retry do mesmo node reaproveita run B via idempotência (sem duplicar).

## 10. Limitações reconhecidas

- **Detecção de ciclos no Builder:** apenas autorreferência direta é detectada no Health (single-graph analysis). Ciclos A→B→A entre fluxos distintos exigiriam análise cross-flow no Builder — proteção total delegada ao Runtime (`__flow_connection_stack` + `MAX_FLOW_CONNECTION_DEPTH=5`). Documentado como decisão pragmática.
- **Modelo C (subfluxo com retorno):** não implementado. Fora do escopo desta missão.
- **Provider WhatsApp real:** validação E2E completa em produção fica para o piloto WebMarcas (mesmo padrão dos blocos anteriores).
