## 3. Contrato do bloco

```ts
{
  kind: "randomizer",
  data: {
    mode: "weighted",
    routes: [
      { id: "route_xyz", label: "Vendas",  weight: 70 },
      { id: "route_abc", label: "Suporte", weight: 30 }
    ]
  }
}
```

- IDs **imutáveis** — gerados na criação (`route_<8 hex>`). Renomear label ou alterar peso NÃO altera id. Reordenação preserva ids.  
- Handles dinâmicos via `getHandles(data)` — uma saída por rota; label exibido `"{weight}% · {label}"`.  
- Mínimo 2 rotas, máximo 10.

## 6. Algoritmo (função pura)

`pickWeightedRoute(routes, rnd)` — exportado de `flow-executor.server.ts`:

1. filtra rotas com peso > 0;  
2. `total = Σ weight`; `r = clamp(rnd, 0, 0.9999999999) * total`;  
3. varre acumulando; devolve a primeira rota onde `r < acc`; fallback: última ativa.

Injetável em teste via `ctx.variables.__randomizer_rng` (número ou
função). Em produção usa `Math.random()`.

### Fronteiras (testes determinísticos)

| rnd | 70/30 → escolhido |
|---|---|
| 0 | route_a |
| 0.6999 | route_a |
| 0.70 | route_b |
| 0.9999 | route_b |
| 1.0 (clampeado) | route_b |

## 7. Runtime / Executor

`randomizerNode` registrado em `NODE_PLUGINS.randomizer`. Fluxo:

1. Parse defensivo das rotas (`parseRandomizerRoutes`).  
2. Falha (`status: "failed"`) se rotas < 2 ou soma ≠ 100.  
3. Consulta `ctx.variables.__randomizer_choices[node.id]` — se existir
   e a rota ainda estiver na config, **reutiliza** (`reused_prior_choice: true`).  
4. Caso contrário, sorteia via `pickWeightedRoute`.  
5. Retorna `nextHandle = chosen.id`, `output` (mode, route_count,
   selected_route_id, selected_route_label, selected_weight,
   reused_prior_choice), e `vars: { __randomizer_choices: { ...prev, [nodeId]: choice } }`.  
6. O loop canônico persiste `variables` no `flow_runs` a cada step → decisão sobrevive a restarts / retomadas.

**Nunca** cria executor paralelo — reusa 100% do pipeline canônico.

## 8. Idempotência / Retry

Provado por teste E2E interno:

- 1º call com `rnd=0.1` escolhe `route_a`.  
- 2º call, mesmo node/run, com `rnd=0.9` (que sortearia `route_b`) e
  `__randomizer_choices.n1 = route_a` presente → devolve **route_a** e
  `reused_prior_choice: true`.  
- Edição posterior da config removendo a rota escolhida → re-sorteia
  (fail-safe explícito).

## 9. Isolamento por node / run

Chave é `node.id`. Dois randomizers `n1` e `n2` no mesmo run mantêm
decisões independentes — teste dedicado valida (`ISOLAMENTO POR NODE`).

Multi-tenant: o bloco não acessa recursos externos. `variables` já é
escopado ao `run_id` (que pertence a `company_id`), portanto nenhum
estado atravessa tenants.

## 10. Observabilidade

Cada execução grava em `flow_run_steps.output`:

```json
{
  "mode": "weighted",
  "route_count": 2,
  "selected_route_id": "route_xyz",
  "selected_route_label": "Vendas",
  "selected_weight": 70,
  "reused_prior_choice": false
}
```

Consulta “Qual caminho este contato seguiu?” → 1 linha em
`flow_run_steps` filtrando por `run_id` + `node_type = 'randomizer'`.

## 11. Round-trip

Teste `round-trip preserva IDs, labels e pesos das rotas` valida
`Serializer.roundTrip(graph)` — dados idênticos entrando e saindo,
incluindo edges apontando para `sourceHandle = route.id`.

## 12. Publicação

Health impede publicar quando soma ≠ 100 ou rota com peso > 0
desconectada. Configuração 60/40 válida → publica; versão preserva
IDs (round-trip garantido).

## 13. Modo Sequencial

Não implementado nesta subetapa. Requer estado atômico compartilhado
(`SELECT ... FOR UPDATE` ou upsert com incremento em nova tabela
`randomizer_state(company_id, flow_id, node_id, cursor)`).  
UI apresenta apenas o modo Aleatório — não há opção configurável
“Sequencial” hoje. Nenhuma promessa falsa no BlockCard.
