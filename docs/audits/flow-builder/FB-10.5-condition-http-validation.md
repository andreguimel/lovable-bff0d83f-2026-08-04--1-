# FB-10.5 — Condition Engine Real + HTTP/API Segura

**Escopo:** última missão funcional do Flow Builder V1. Fecha os dois gaps essenciais identificados pela FB-10.4E:

- **G1 · Condition**: executor era placeholder regex sobre `expression`. Não avaliava `ctx.variables`.
- **G2 · HTTP/API**: executor fazia `fetch` "cru", sem headers/auth/interpolação/SSRF guard/timeout, e não persistia resposta em variável.

Nada fora deste escopo foi tocado: sem novos blocos, sem refactor no runtime canônico, sem alteração em Provider, Registry, RBAC, RLS, Server Functions ou Design System.

---

## 1. G1 — Condition Engine real

### 1.1 Alterações UI/Schema (`blocks/definitions.ts`)

Kind `condition` passa a expor três campos estruturados **além** do modo legado `expression`:

- `field` — path dotted em `ctx.variables` (ex: `contact.name`, `contact.tags`, `http.status`, `ai.output`, `last_message`).
- `operator` — `equals`, `not_equals`, `contains`, `not_contains`, `gt`, `gte`, `lt`, `lte`, `exists`, `not_exists`.
- `value` — literal ou variável `{{...}}`. Oculto quando o operador é `exists`/`not_exists`.

`validate()` exige `field` + `operator` (e `value` quando aplicável) no modo estruturado. O modo `expression` legado permanece válido para nós antigos.

Preview humano:
- Estruturado → `Se contact.tags contains VIP` / `Se ai.output existir`.
- Legado → `Se ${expression}` (compatibilidade).

Saídas continuam sendo `true` / `false` (IDs estáveis, sem colisão com o legado).

### 1.2 Runtime (`flow-executor.server.ts` → `conditionNode`)

- `getByPath(vars, "a.b.c")` resolve caminho ponto sem lançar em chaves ausentes.
- `evalConditionOp(left, op, right)` implementa os 10 operadores. `contains`/`not_contains` cobrem string (case-insensitive) e array. `gt`/`gte`/`lt`/`lte` convertem para `Number`. `exists`/`not_exists` cobrem `null | undefined | ""`.
- `value` é interpolado via `resolveVars(..., ctx.variables)` antes da comparação → suporta `{{ai.output}}`, `{{contact.id}}`, etc.
- Fallback legado (`expression`) mantido para compatibilidade com fluxos publicados antes desta missão.
- Retorna `output.mode: "structured" | "legacy"`, `result: boolean`, e `nextHandle: "true"|"false"`.

### 1.3 Testes (`src/lib/__tests__/flow-executor-condition.test.ts`)

9 cenários, todos PASS:

- equals verdadeiro/falso → `true`/`false`.
- `contains` em string (case-insensitive) e em array (`contact.tags` inclui `VIP`).
- `gt`/`gte` numérico (`http.status` vs 200/500).
- `exists`/`not_exists` cobrem `""`, `undefined`, path inexistente.
- Interpolação `{{expected}}` no `value`.
- Path aninhado inexistente devolve `false`.
- Modo legado (`expression: "contact é VIP"`) continua roteando por `true`.

## 2. G2 — HTTP/API Segura

### 2.1 Alterações UI/Schema (`blocks/definitions.ts` → `http_request`)

Novos campos:

- `headers` (`textarea`) — pares `Chave: Valor` por linha, com `{{...}}`.
- `auth_type` — `none | bearer`.
- `auth_token` — visível apenas quando `bearer`. Aceita `{{...}}`.
- `body` — visível para métodos ≠ GET/HEAD. Aceita `{{...}}`.
- `timeout_ms` — 500–30000, default 10000.
- `save_as` — nome da variável de saída (default `http`).

Bloco informativo declara o SSRF guard para o operador.

`validate()`:
- URL obrigatória. Se **literal** (sem `{{...}}`), valida esquema http/https.
- `auth_type=bearer` exige `auth_token`.

### 2.2 Runtime (`flow-executor.server.ts` → `httpNode` + helpers exportados)

Guardas de segurança:

- **Esquema restrito**: apenas `http:` e `https:` (bloqueia `file://`, `gopher://`, etc.).
- **SSRF guard** (`isPrivateHost`): bloqueia `localhost`, `0.0.0.0`, `127.0.0.0/8`, `10.0.0.0/8`, `192.168.0.0/16`, `169.254.0.0/16` (inclui IMDS `169.254.169.254`), `172.16.0.0/12`, IPv6 `::1`, `fc00::/7`, `fe80::/10`.
- **Timeout** via `AbortController` com `clearTimeout` no `finally` implícito; erro `AbortError` vira `status: "failed"` com mensagem clara e `metrics.http_aborted: true`.
- **Body truncado** a 8 KB antes de ir para `output` e para a variável (evita explodir `flow_run_steps`).

Interpolação `{{...}}` aplicada em: URL, valores de headers, `auth_token`, `body`.

Auth Bearer é montado server-side (`Authorization: Bearer <token>`), com token opaco resolvido de variáveis — o token literal nunca precisa aparecer no builder se o operador usar `{{secrets.api_token}}`.

Persistência da resposta em `ctx.variables[save_as]` (`http` por default) com shape estável:

```json
{ "ok": true, "status": 200, "headers": { ... }, "body": <json | string> }
```

O `body` é tentado como JSON; se falhar, permanece como string. Isto habilita `{{http.body.field}}`, `{{http.status}}` em blocos subsequentes (Condition, Message, IA, etc.).

`dryRun`: não chama `fetch`, ainda emite `vars.<save_as> = { dry_run: true, url, method }` para o Test Runner.

### 2.3 Testes (`src/lib/__tests__/flow-executor-http.test.ts`)

10 cenários com `global.fetch` mockado, todos PASS:

- SSRF guard: bloqueia `localhost`, `169.254.169.254`, `10.0.0.1`, `192.168.1.1`, `172.16.0.5` — **nenhum `fetch` disparado**.
- Bloqueia `file://`.
- GET público 200 → `status: "ok"` e variável `resp.body.hello === "world"`.
- POST com interpolação em URL/headers/body/bearer → mock recebe `https://api.example.com/abc`, `X-Trace: T1`, `Authorization: Bearer TOKEN`, `body: {"name":"Ana"}`, `Content-Type: application/json` automático.
- 500 → `status: "failed"` mas `vars.http` ainda persistido para ramo de erro (Condition consegue avaliar `http.status`).
- Timeout com fetch mockado que respeita `AbortSignal` → `status: "failed"`, mensagem `Timeout após 50ms`.
- `dryRun` não chama `fetch`.
- URL vazia → `skipped`.
