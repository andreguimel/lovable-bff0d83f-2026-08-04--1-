## 6. Runtime canônico

Novo `actionNode` registrado em `NODE_PLUGINS` (kind `action`) dentro do executor canônico único (`src/lib/flow-executor.server.ts`). Nenhum executor paralelo criado. O executor:

1. Lê `action_type` de `node.data`.
2. Faz **guarda de tenant** (`assertTagBelongsToCompany` / `assertUserBelongsToCompany`) antes de mutar.
3. Aplica a mutação idempotente:
   - `add_tag` → `contact_tags.upsert({ onConflict: "contact_id,tag_id", ignoreDuplicates: true })`.
   - `remove_tag` → `DELETE` filtrado por `company_id` (no-op quando ausente).
   - `assign_agent` → `UPDATE` filtrado por `company_id` (converge para o estado desejado).
4. Emite output rico (`action`, `tag_id`, `tag_name`, `contact_id`, `conversation_id`) coletado pelos `flow_run_steps` + `flow_events` já existentes.
5. Segue pelo handle `default` como qualquer outro plugin.

`dryRun=true` (Playground) não persiste nada e retorna `{ dry_run: true }`.

## 9. Segurança multi-tenant

- `assertTagBelongsToCompany` e `assertUserBelongsToCompany` fazem `SELECT ... eq(company_id, ctx.companyId)` **antes** de qualquer `INSERT`/`UPDATE`/`DELETE`.
- Todos os mutation paths adicionam `.eq("company_id", ctx.companyId)` como cinto extra.
- Cobertura de teste explícita:
  - Etiqueta da Empresa B com run da Empresa A → `failed` + zero linhas alteradas.
  - Atendente da Empresa B com run da Empresa A → `failed` + `assigned_user_id` permanece `null`.
